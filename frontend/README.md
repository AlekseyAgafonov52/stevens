# Stevens — React frontend

React 19 + TypeScript strict + Vite. Дизайн и исходные материалы — из `stevens-front.zip`: IBM Plex, CSS-токены, светлая/тёмная системная тема, центральная лента, карточки и кнопки. Python-бэкенд не изменён.

## Запуск

Нужен Node.js 22.13 или новее (проверено на 24.19). Для повторяемой установки используется pnpm 11.25.0 и `pnpm-lock.yaml`. Команды из папки `frontend`:

```powershell
npm install --global pnpm@11.25.0
pnpm install --frozen-lockfile
pnpm dev
```

Обычный запуск обращается к реальному API на http://localhost:8000. Для успешного входа и чата бэкенд должен работать отдельно. Live Server не используется: TSX обрабатывается Vite. Адрес фронта — http://127.0.0.1:5173.

В среде Codex зависимости уже установлены. Если `npm` не найден, установите Node.js и заново откройте терминал VS Code. Альтернативный запуск на этом Windows-компьютере — `./start.ps1`: он находит обычный Node или bundled Node Codex и запускает установленный Vite. Скрипт не устанавливает пакеты и не меняет настройки системы.

## Демонстрация без сервера

Демонстрация включается только явно: `pnpm dev:mock`. Она использует `.env.minimal` с `VITE_API_MODE=mock`. Обычные dev, production и full настроены на real.

На экране входа нажать «Попробовать без регистрации» или войти с любым корректным email и паролем. Для регистрации требуется имя и пароль от 6 символов. `taken@example.com` при регистрации имитирует занятый email, пароль `wrong` при входе — неправильные данные.

Проверить пять примеров. Дополнительные команды: `#network`, `#timeout`, `#slow`, `#500`, `#401`, `#wake`, `#unknown_kind`, `#list_mixed`, `#backend_error`. Моки используют фиксированные часы `2026-10-21T10:00:00+03:00`, поэтому пример «завтра» всегда показывает 22 октября. Это демонстрация готовых ответов, не настоящая база, не LLM и не серверная песочница.

## Подключение существующего бэкенда

Если нужно изменить адрес бэка, создать `frontend/.env.development.local` по `frontend/.env.example`:

```dotenv
VITE_API_MODE=real
VITE_API_URL=http://localhost:8000
VITE_FEATURE_AUTH=true
```

Перезапустить Vite. Python-сервер и PostgreSQL запускаются отдельно из корня репозитория. Для backend нужен корневой `.env` с `DATABASE_URL`, `YANDEX_API_KEY`, `YANDEX_FOLDER_ID` и установленные зависимости. Текущий requirements.txt неполный: это отдельный блокер запуска backend, фронтенд его не исправляет.

В real режиме зарегистрироваться через имя/email/пароль или войти через email/пароль. Гостевой режим скрыт. Передаются Bearer-токен и фактический формат `ChatRequest`. Проверка доступности — `GET /`, поскольку `/api/health` в backend отсутствует. Это проверка доступности HTTP, а не работоспособности LLM.

Всё, что начинается с `VITE_`, доступно браузеру. Ключи Yandex и строку базы никогда не добавлять в frontend env.

## Структура

```text
src/api/            Реальный API, моки, Zod, типы и ошибки
src/components/     Карточки, кнопки, модальное окно, ErrorBoundary
src/features/auth/  Экран email-авторизации
src/features/chat/  Лента, ответы, ввод и состояние диалога
src/voice/          Изолированный адаптер Web Speech API
src/storage/        Сессия и история с защитой при недоступном localStorage
src/lib/            Часы и форматирование дат
src/content/        Тексты интерфейса
src/config/         Режим API и флаги
src/styles/         Токены из архива и стили компонентов
docs/               Исходная спецификация и backend-integration.md
```

История хранится отдельно для mock/real и аккаунтов, до 50 сообщений на 60 минут. После восстановления кнопки неактивны; незавершённое сообщение возвращается в поле. Токены разделены по режиму и URL сервера. Выход удаляет токен локально — серверного logout пока нет.

## Проверки

```powershell
npm run lint
npm run typecheck
npm test
npm run build
```

`build:minimal` собирает демонстрацию без экрана входа. Обычный `build` и `build:full` используют реальный API. Адрес для хостинга задаётся до сборки: переменной окружения процесса либо в соответствующем `.env.production.local` / `.env.full.local`. Файл режима имеет приоритет над общим `.env.local`, а переменные процесса — над файлами. После изменения адреса нужна новая сборка. Адрес должен быть доступен браузеру пользователя, без добавления `/api` в конце.

## Фронтенд через Docker

Из папки `frontend`, при запущенном Docker Desktop:

```powershell
Copy-Item .env.docker.example .env.docker.local
docker compose --env-file .env.docker.local config
docker compose --env-file .env.docker.local up --build -d
docker compose --env-file .env.docker.local ps
```

Открыть http://localhost:8080. Проверка контейнера: http://localhost:8080/healthz. Остановка: `docker compose --env-file .env.docker.local down`.

Перед сборкой установить `VITE_API_URL` в `.env.docker.local`: для локальной проверки оставлен `http://localhost:8000`, для размещения на сервере нужен настоящий публичный HTTPS-адрес бэка. `localhost` означает компьютер посетителя; имя контейнера вроде `backend` браузер обычно не видит. В этом варианте Nginx отдаёт сайт, а браузер обращается к API напрямую: бэк должен разрешать origin сайта в CORS. Для голоса на публичном сайте нужен HTTPS; localhost подходит для локальной проверки.

Dockerfile собирает приложение на Node.js, запускает проверки и копирует результат в Nginx. Docker всегда использует real и авторизацию; локальные env, node_modules и секреты в контекст сборки не попадают. Адрес API встраивается при сборке, не при старте Nginx: после изменения URL повторить `up --build -d`.

Этот Compose запускает только фронт. Корневой docker-compose.yml запускает отдельно PostgreSQL; FastAPI и YandexGPT настраивает бэкендер. Работа `/healthz` подтверждает только исправность контейнера фронта, не доступность API или модели.

## Проверка перед совместной приёмкой

1. Запустить бэк с PostgreSQL, ключами Yandex и полным набором Python-зависимостей.
2. Разрешить в CORS фактический origin фронта: при локальном Docker это http://localhost:8080, при Vite — http://127.0.0.1:5173.
3. Зарегистрироваться или войти в реальный аккаунт. В Network браузера должны быть запросы к настоящему API, а не локальные ответы mock.
4. Создать задачу уникальным текстом, получить её в списке и найти поиском. Убедиться, что это запись БД, а не только сохранённая история браузера.
5. Проверить микрофон: в /api/chat отправляется распознанный текст с source=voice. Проверить отмену и сохранение длинного текста для редактирования.
6. Проверить неверный пароль, истёкший токен, недоступность бэка и обновление страницы.

Статус на 21.10.2026: 24 модульных теста проходят. Сквозная работа с реальными БД/LLM и запуск Docker-контейнера ещё не подтверждены. Из среды Codex получен отказ доступа к Docker API; Compose-конфигурация проверена отдельно.

## Границы первой версии

- Реальная песочница, серверный сброс и серверный выход отсутствуют: запросы на вымышленные маршруты не отправляются.
- Текущий backend не обрабатывает action и не хранит уточнения. Действия в real режиме показывают понятную ошибку; в mock режиме работают по готовым сценариям. Быстрые текстовые ответы передаются как есть, но завершение уточнения потребует доработки backend.
- Поиск/периоды/проверки дат ограничены реализацией Python. Фронтенд не исправляет ответы сервера и не использует небезопасный `/tasks` для загрузки чужих записей.
- Голос: Web Speech API, ru-RU, автоматическая отправка при остановке/тишине, отмена при скрытии вкладки, лимит 20 секунд. Поддержка зависит от браузера; текст работает независимо. Реальную запись с микрофона нужно проверить вручную. Индикатор громкости пока не реализован.
- Проверка сервера не ставит сообщения в очередь пробуждения; сетевой сбой обрабатывается обычной ошибкой с повтором.
- Полная финальная приёмка всех пунктов исходного плана ещё впереди; это первая рабочая версия, а не заявление о выполнении всех требований хакатона.
