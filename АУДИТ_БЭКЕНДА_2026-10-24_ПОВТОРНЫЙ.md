## Новые подтвержденные замечания

### N1. Импорт может сохранить повторяющиеся встречи без времени

**Высокий приоритет надежности.** Место: `app/routers/transfer.py:253–294`, особенно проверка на строке 288.

Создана ежедневная серия встреч с `time: "10:00"`. Затем импортирована правка:

```json
[{"id":"s<ID_СЕРИИ>","time":null}]
```

Ответ: HTTP 200, `errors: []`. В БД получено **365 событий встречи с `time IS NULL`**. Для обычного PATCH такая встреча не прошла бы проверку: дата и время обязательны.

Причина: ветка правки серии проверяет обязательность времени только для `busy`, но не для `meeting`/`reminder`. Это создает некорректные записи и выключает их уведомления: `push.fire_at()` пропускает запись без времени.

Рекомендация: единая проверка инвариантов для обычной записи, серии и импорта; запретить `null` для времени встреч/напоминаний до любых изменений БД. Добавить регрессию на каждую разновидность серии.

### N2. Ошибка создания серии оставляет часть импортируемого пакета записанной

**Высокий приоритет надежности.** Места: `app/routers/transfer.py:356–377`, `app/series.py:78`.

Воспроизведение:

1. Пакет состоит из обычной новой задачи и новой серии.
2. Передан `client_time: "9999-12-31T12:00:00"`, начало серии тоже `9999-12-31`.
3. Предпросмотр возвращает 200 и `add: 2`.
4. Применение возвращает **500** из-за переполнения даты при вычислении горизонта серии.
5. Проверка отдельной сессией БД показывает: обычная задача **уже сохранена**.

Причина: обработчик сначала выполняет `db.commit()`, затем создает серии отдельными вызовами `series.create()`, каждый из которых тоже делает commit. Возникает неопределенный для клиента частичный результат. Повтор запроса после 500 способен добавить обычные записи повторно.

Контракт намеренно применяет строки без ошибок, а не требует отмены всего пакета при любой ошибке строки. Дефект здесь — неожиданный 500 после фиксации данных без точного ответа, какие строки применены.

Рекомендация: полностью проверять даты до применения; определить транзакционные границы и возвращать результат каждой строки. При частичном применении использовать savepoint и явно фиксируемые результаты; добавить idempotency key для безопасного повтора. Внутренние `commit()` из функций создания серии нужно убрать или вынести под управление вызывающего обработчика.

### N3. Неверный id в импорте приводит к HTTP 500

**Средний приоритет.** Места: `app/routers/transfer.py:159–162, 297–313`.

Подтверждены 500 на:

- `id: []`, `id: {}`, `id: [1]` — непригодное для множества значение попадает в `rid in seen` / `seen.add()`;
- целочисленный id порядка `10**70`;
- строку `s` с 70 цифрами — значение выходит за диапазон используемого SQL-идентификатора.

`id: true` вернул 200 с ошибкой строки, а не 500: это отдельно не классифицируется как обход владения.

Рекомендация: схема входной строки с разрешенными типами id, явным запретом bool и проверкой диапазона по типу колонок БД; некорректные значения превращать в 422 или описанную ошибку строки. Проверять id до SQL-запроса и множества `seen`.

### N4. Экспорт не отражает все свойства расписания

**Средний/высокий приоритет целостности данных.** Место: `app/routers/transfer.py:58–94`.

Подтверждены два случая:

1. У задачи с `date_kind=deadline` экспорт содержит `id,type,text,date,time,status`, но **не содержит `date_kind`**. Получатель не может отличить срок «до даты» от задачи «на дату».
2. У отдельного события повторяющейся встречи изменены текст, время и `remind_before`. Экспорт представляет серию одной общей строкой: **исключение отсутствует** — ни id измененного события, ни его измененный текст не вошли в выгрузку.

Непосредственный повтор неизмененной выгрузки в тот же аккаунт может оставить такие исключения в БД, поэтому не утверждается, что любая кнопка «Применить» сразу их стирает. Проблема в неполном представлении данных для внешнего ИИ, переноса и возможного восстановления. Выгрузку нельзя считать полноценным backup.

Рекомендация: экспортировать `date_kind`, свойства уведомлений и исключения/переносы/удаления отдельных событий серии; версионировать формат. Если экспорт намеренно упрощенный, явно описать ограничения интерфейса и документации. Нужен тест сохранения семантики расписания после export → обработка → import.

### N5. Некорректные дни недели в правке серии молча заменяются прежними

**Средний приоритет.** Место: `app/routers/transfer.py:265–268`.

Правка существующей серии с `repeat.weekdays: [99]` вернула 200 и пустой массив `errors`. Неверный список подменяется прежним значением выражением `weekdays_of(...) or before[...]`. Пользователь получает успешный ответ на ошибочный ввод.

Рекомендация: различать отсутствие поля и неверное значение; для некорректных дней возвращать ошибку строки. Проверка новых и существующих серий должна быть одинаковой.

### N6. WebM отправляется провайдеру с параметром формата Ogg Opus

**Средний приоритет функциональности.** Места: `app/routers/client.py:19, 43–58`; `frontend-contract/src/voice/index.ts:387–403`.

Фронтенд может записывать `audio/webm;codecs=opus`. Сервер разрешает `audio/webm`, но без преобразования задает `format=oggopus` для любого аудио.

В тесте перехвачен исходящий запрос с первыми байтами WebM `1a45dfa3` и query-параметром `format=oggopus`. Настоящему Yandex аудио не отправлялось: расхождение контейнера и объявленного формата подтверждено, конкретный ответ провайдера не проверен. Ответ 200 в этой проверке создан заглушкой и не доказывает работу настоящего распознавания.

Рекомендация: согласовать принимаемый контейнер с форматом запроса провайдеру; при необходимости конвертировать WebM в поддерживаемый формат либо использовать API, явно поддерживающий WebM. Покрыть запись из реального браузера и распознавание без подмены транспорта.

### N7. Выключенная чат-функция остается доступна через action

**Средний приоритет согласованности конфигурации.** Места: `app/features.py:30–34`, `app/routers/chat.py:2698–2705, 2847`.

При `STEVENS_FEATURES=f7` отправлена команда `action: {id:"delete", record_id:...}` с клиентским `X-Stevens-Features: d2,d3,d10`. Несмотря на выключенную `f12`, ответ — 200, `kind=deleted`; запись действительно мягко удалена.

Причина: `handle_action()` выполняется до серверной проверки feature flag по распознанному намерению. Feature flags не являются системой прав доступа, и это **не обход изоляции аккаунтов**. Но сервер не соблюдает заявленное отключение функции для action-запроса.

Рекомендация: применять серверные флаги и к текстовому намерению, и к кнопочным действиям, независимо от клиентского заголовка. Зафиксировать, распространяются ли флаги на прямые REST/transfer API.

### N8. Длинный конечный повтор обрывается через год и не продлевается

**Высокий приоритет надежности расписания.** Места: `app/series.py:78, 102–104`. Это ранее существовавший дефект неизмененного модуля, впервые выявленный этим аудитом.

Импортирована ежедневная серия до `2028-10-24`. Получено 200. В БД `until=2028-10-24`, но `filled_until=2027-10-24`. Вызов продления с датой `2027-09-01` оставил `filled_until` прежним.

Причина: создание ограничено годовым горизонтом для любых серий, но `extend()` выбирает только `until IS NULL`. Конечные серии дольше года не продолжаются, хотя пользователь задал более поздний конец.

Рекомендация: продлевать и конечные серии, ограничивая очередную порцию минимумом из горизонта и `until`; проверять число событий и последнюю дату после продления. Нужны регрессии для конечной серии дольше года, завершенной серии и границ календаря.

| Низкий | `security.generate_token()` по-прежнему задает 7 дней, активный роутер — 30 | Неиспользуемый дубль удалить либо объединить конфигурацию TTL |

## Что проверками не сломано

- Обычная регистрация/вход, срок и отзыв токена, неверный Bearer → 401.
- Изоляция записей: чужие PATCH/DELETE/restore возвращают 404; импорт чужого id сообщает отсутствие записи и не меняет оригинал. В проверенных сценариях обход владения аккаунтом не обнаружен.
- Обычный предпросмотр импорта новой задачи оставляет БД пустой; применение сохраняет 1 запись. Ограничение 1001 входной строки возвращает 422 `too_many`.
- Обычная правка повторов и повтор неизмененной выгрузки проходят штатные тесты. Это не покрывает N1–N5.
- STT без ключа возвращает 503, неверный Content-Type — 415, тело больше лимита — 413. Реальный успешный STT не подтвержден.
- Повторный сценарий двух параллельных подтверждений дал `created` и `not_understood`, без двух созданных записей; это не исчерпывающая проверка гонок.
- Глубоко вложенный синтетический JSON в новом тесте вернул 200 с обработанным результатом; падение на этой конкретной проверке не получено.
- Совместимость Python-пакетов, синтаксис исходников и frontend quality checks пройдены.

## Приоритет исправлений

1. Закрыть прежние риски аутентификации и push: длинные пароли, endpoint/SSRF, владение подписками, типизированный payload.
2. До массового применения импорта исправить N1–N3: единая валидация, предсказуемая фиксация данных, idempotency и диапазоны id/дат.
3. Исправить доставку push и долгие конечные повторы: пользователю нельзя обещать уведомления/расписание, которые фактически исчезают.
4. Уточнить формат выгрузки и сохранить семантику сроков/исключений; исправить валидацию дней недели.
5. Согласовать контейнер аудио STT и обработку feature flags для action.
6. Перед публичным доступом добавить quotas/rate limit, закрыть БД, настроить HTTPS/CORS, сроки хранения, readiness и аварийное восстановление.

## Артефакты и повторение

- [audit_run_tests.py](audit_run_tests.py) поддерживает `AUDIT_OUT_DIR`; исправлена передача `sys.argv`, чтобы новые тесты с фильтрами командной строки действительно выполняли полный набор. Создается `backend-status.json`.
- [audit_security_checks.py](audit_security_checks.py) повторяет прежние специальные сценарии и также поддерживает отдельный каталог результатов.
- [audit_v2_new_checks.py](audit_v2_new_checks.py) воспроизводит новые замечания; STT-транспорт подменен, push-цикл при этих проверках отключен. Результат 0 у этого скрипта означает завершение сбора наблюдений, а не отсутствие дефектов.
- [audit_http_smoke.py](audit_http_smoke.py) проверяет HTTP-стенд на `127.0.0.1:18081`, включая новые endpoint.
- [audit-results-v2](audit-results-v2/) содержит исходные наблюдения, 19 серверных логов, сборочные логи, хеши и ревизию.

Скрипты создают и меняют тестовые данные. Для повтора нужна отдельная PostgreSQL с URL, указанным в скриптах; не направлять их на пользовательскую БД. Пример запуска штатных тестов после подготовки отдельной БД:

```powershell
$env:AUDIT_OUT_DIR = 'audit-results-v2'
python audit_run_tests.py
python audit_v2_new_checks.py
```

Первый отчет и каталог `audit-results/` не перезаписаны. Временные контейнеры и сеть второго аудита после проверки удалены; локальные образы с префиксом `stevens-audit2-` оставлены для повторения. Docker Desktop был запущен для проверки и оставлен работающим.

## Ограничения

Не проверялись настоящим браузером визуальные экраны, клики, микрофон, Safari/iOS/PWA, реальный STT и LLM, доставка push на устройство, внешняя доступность сервера, эксплуатация SSRF соединением с внутренним сервисом, длительная нагрузка, несколько серверных воркеров, актуальная база CVE для Python/npm/образов, все секреты в git-истории и восстановление backup. Синтетические тесты используют фиксированное клиентское время; проверка поздних дат и продления выполнялась в изолированной БД.

Это отчет по исходникам и перечисленным локальным сценариям, а не сертификация безопасности production.
